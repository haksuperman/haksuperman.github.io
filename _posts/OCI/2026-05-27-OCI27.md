# 1. 개요
## 1.1. 프로비저닝 방식
1. 동적 프로비저닝
   1. **새로운 스토리지 클래스(StorageClass)를 정의한 후, 생성한 스토리지 클래스 기반으로 새 PVC를 생성하는 방식**
   2. PVC를 생성할 때 CSI Volume Plugin이 **OCI 내에 새로운 File Storage와 이를 백엔드로 하는 PV를 동적으로 자동 생성**
   3. 기존 Mount Target 활용(OCID 지정)하거나, 새 Mount Target 생성 가능

    > 동적 프로비저닝 주의 사항
    >
    > - 자동으로 생성된 모든 File Storage와 Mount Target, Export의 이름은 `csi-fss-` 로 시작
    > - OCI Console에 자동으로 생성된 리소스들이 표시 되긴 하지만, 이를 수동으로 수정하지 않아야 함  
    >   (수동으로 변경한 내용은 Kubernetes와 동기화 되지 않음)
    > - PVC를 삭제하면, CSI Plugin이 자동으로 생성한 File Storage와 PV도 함께 삭제됨
    {: .prompt-info }

2. 정적 프로비저닝
   1. **OCI Console에서 수동으로 File Storage와 Mount Target을 미리 생성해 두는 방식**
   2. 미리 생성한 File Storage를 백엔드로 하는 PV를 정의하고, 새로운 PVC를 정의하여 PVC와 기존 File Storage를 가리키는 PV를 바인딩

## 1.2. 데이터 암호화

- 저장 데이터 암호화 (Data At Rest)
  - 기본적으로 'Oracle 관리형 암호화 키'를 통해 암호화 수행
  - OCI Vault 서비스에서 직접 관리하는 ‘고객 관리형 마스터 암호화 키’를 지정하여 적용 가능

- 전송 중 데이터 암호화 (Data In Transit)
  - 필요 시 선택하여 활성화 가능
  - TLS 1.2 암호화를 적용하여 인스턴스와 마운트된 File Storage 간 전송되는 데이터 암호화 가능
  - Worker Node의 OS가 Oracle Linux 7 혹은 Oracle Linux 8이어야 함

# 2. IAM
## 2.1. CSI Volume Plugin의 File Storage 리소스 권한 부여

```plaintext
# File System, Mount Target, Export Path에 대해 생성 및 관리(manage)할 수 있도록 권한 부여
ALLOW any-user to manage file-family in compartment <compartment-name> where request.principal.type = 'cluster'

# VNIC, Private IP, Private DNS 이용(use)할 수 있도록 권한 부여
ALLOW any-user to use virtual-network-family in compartment <compartment-name> where request.principal.type = 'cluster'
```

## 2.2. (Compartment가 다른 경우) CSI Volume Plugin의 리소스 권한 부여

```plaintext
ALLOW any-user to manage file-family in TENANCY where request.principal.type = 'cluster'
ALLOW any-user to use virtual-network-family in TENANCY where request.principal.type = 'cluster'
```

# 3. (Optional) Mount Target 생성
- CSI Volume Plugin은 새 File System을 생성하기 위해 Active 상태의 Mount Target(IP 주소가 할당된)이 필요함
- 기존 Mount Target을 활용하려는 경우, OCI Console에서 미리 직접 생성  
  -> 미리 생성하지 않는 경우, StorageClass 정의할 때 Mount Target을 생성할 서브넷을 지정해야 함

# 4. StorageClass 생성
- File System 동적 생성을 담당할 fss.csi.oraclecloud.com 프로비저너를 사용하는 StorageClass를 신규 정의


## 4.1. YAML 매니페스트 파일 작성

```yaml
kind: StorageClass
apiVersion: storage.k8s.io/v1
metadata:
  name: oke-fss-dynamic-sc   # 원하는 스토리지 클래스 이름
provisioner: fss.csi.oraclecloud.com
parameters:
  availabilityDomain: AAAAA:AP-SEOUL-AD-1   # 예: US-ASHBURN-AD-1
  
  # mountTargetOcid: <mt-ocid>   # 기존 마운트 타겟을 사용할 경우
  mountTargetSubnetOcid: ocid1.subnet.oc1.ap-seoul-1.aaaaaaaafmpcaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa   # 마운트 타겟을 새로 생성할 서브넷 지정 시
  compartmentOcid: <compartment-ocid>   # (Optional) 생략 시 클러스터와 동일한 구획에 생성됨
  exportPath: /oke-fss-exportpath-01   # (Optional) FSS 내 익스포트 경로
  encryptInTransit: "false"   # (Optional) 전송 중 암호화 적용 여부 ("true" 또는 "false")
```

# 6. PVC
## 6.1. YAML 매니페스트 파일 작성

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: oke-fss-dynamic-pvc
spec:
  accessModes:
    - ReadWriteMany
  storageClassName: oke-fss-dynamic-sc # 위에서 생성한 StorageClass 이름과 정확히 일치해야 함
  resources:
    requests:
      storage: 50Gi   # 지정한 값과 관계 없이 기본 크기의 File System 생성 (Kubernetes에서 반드시 지정해야 해서 지정하는 것일 뿐)
```

![image](/assets/img/posts/OCI/OCI27_06.png)

## 6.2. PVC 생성 및 확인

```bash
# PVC 생성
kubectl apply -f ./fss-dynamic.pvc

# PVC 확인
kubectl get pvc
```

![image](/assets/img/posts/OCI/OCI27_07.png)

## 6.3. FSS 결과 확인

- PVC 생성 시, StorageClass에서 명시한 `provisioner: fss.csi.oraclecloud.com` 에 의해 CSI Volume Plugin은 PV 및 File System을 자동 생성
- 기존 Mount Target을 지정하지 않은 경우, Mount Target도 함께 자동 생성

> 생성된 PVC는 자동 생성된 PV에 자동 바인딩 됨
> - 데이터는 암호화되어 저장되며, 암호화 키는 Oracle 관리 키 or OCI Vault를 통한 고객 관리형 키에 의해 지정

# 7. Pod
## 7.1. YAML 매니페스트 파일 작성

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx
spec:
  containers:
    - name: nginx
      image: docker.io/library/nginx:latest
      ports:
        - name: http
          containerPort: 80
      volumeMounts:
        - name: fss-volume
          mountPath: /usr/share/nginx/html   # 컨테이너 내부의 마운트 경로
  volumes:
    - name: fss-volume
      persistentVolumeClaim:
        claimName: oke-fss-dynamic-pvc   # 위에서 생성한 PVC 이름
```

> **객체 수동 삭제**
>
> 매니페스트 파일을 통해 수월하게 삭제 가능  
> 단, 수동으로 객체들(Pod, StorageClass, PV, PVC, Block Volume 등)을 삭제하는 경우 정확한 순서를 지켜야 한다.
>
> 1. StorageClass의 Reclaim Policy (회수 정책)이 Delete로 설정된 경우
>    1. 파드 삭제 (볼륨 마운트 해제)
>    2. PVC 삭제  
>       (PV와 OCI Block Volume은 자동으로 삭제)
>    3. StorageClass 삭제
>
>   ```bash
>   # 파드 삭제
>   kubectl delete pod nginx
>   
>   # PVC 삭제
>   kubectl delete pvc oke-fss-dynamic-pvc
>   
>   # StorageClass 삭제
>   kubectl delete sc oci-fss-dynamic-sc
>   
>   # 삭제 확인
>   kubectl get sc,pod,pvc,pv
>   ```
>
> 2. StorageClass의 Reclaim Policy(회수 정책)이 Retain으로 설정되어 있는 경우 / 시스템 오류로 수동 삭제해야 하는 경우
>    1. 파드 삭제 (볼륨 마운트 해제)
>    2. PVC 삭제
>    3. PV 삭제
>    4. OCI File Storage 리소스(Export → File System → Mount Target) 삭제
>    5. StorageClass 삭제
>
>   ```bash
>   # 파드 삭제
>   kubectl delete pod nginx
>   
>   # PVC 삭제
>   kubectl delete pvc oke-fss-dynamic-pvc
>   
>   # PV 삭제
>   kubectl delete pv csi-d577e928-095a-44d7-8a3a-2aef69d20b8a
>   
>   # File Storage 리소스(Export -> File System -> Mount Target) 삭제
>   # (OCI Console 내 삭제 확인)
>   
>   # StorageClass 삭제
>   kubectl delete sc oci-fss-dynamic-sc
>   
>   # 삭제 확인
>   kubectl get sc,pod,pvc,pv
>   ```
