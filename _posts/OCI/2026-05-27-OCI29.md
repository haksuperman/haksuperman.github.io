## 1. Node Cycling 개념

### 1.1. 개요

Node Cycling은 기존 Node Pool의 설정을 변경한 뒤, 기존 Worker Node에 변경 사항을 반영하기 위해 노드를 순차적으로 교체하거나 Boot Volume을 교체하는 운영 기능이다.

이를 통해 운영자는 수동 Cordon, Drain, Node Terminate 작업을 줄이고, OKE가 제공하는 표준 절차에 따라 노드 업데이트를 수행할 수 있다.

### 1.2. Node Pool 업데이트와 기존 Worker Node 반영

OKE에서 Node Pool의 Kubernetes 버전, OS 이미지, SSH Key, Node Metadata 등의 속성을 변경하면, 변경 사항은 새로 생성되는 노드에만 적용된다. (기존 Worker Node에는 반영되지 않음)

기존 Worker Node에 변경 사항을 적용하려면 다음 중 하나의 방식이 필요하다.

1. 기존 노드를 수동으로 Cordon, Drain, Terminate한 후 새 노드로 교체한다.
2. 새 Node Pool을 생성한 뒤 워크로드를 이전하고 기존 Node Pool을 삭제한다.
3. Node Cycling을 사용하여 기존 Node Pool 내의 노드를 자동으로 순차 업데이트한다.

> 본 문서에서는 3번 Node Cycling에 대한 내용을 다룬다.
{: .prompt-info }

### 1.3. Node Cycling 방식

Node Cycling을 실행하면 OKE는 설정된 옵션에 따라 기존 Worker Node를 Cordon 및 Drain하고, 아래 방식 중 하나의 방식으로 노드를 업데이트한다.

#### 1.3.1. Replace nodes
기존 Worker Node를 Cordon 및 Drain한 후 종료하고, 동일 Node Pool 내에 새 Worker Node를 생성한다.
- 기존 인스턴스를 Terminate하고, 새 인스턴스를 생성한다.
- Kubernetes 버전 업그레이드, 이미지 변경, Shape 관련 변경, 태그 및 기타 Node Pool 속성 반영에 적합하다.
- maxSurge 값을 사용하면 일시적으로 Node Pool의 노드 수가 증가할 수 있다.
- Replace nodes 방식에서는 기존 Compute Instance가 Terminate되고 새 Instance가 생성되므로, Instance OCID와 네트워크 주소가 변경된다.

#### 1.3.2. Replace boot volume
기존 Worker Node가 실행 중인 인스턴스 자체는 유지하고, Boot Volume을 교체한다.<br>
OKE는 노드를 Cordon 및 Drain한 뒤 Boot Volume을 교체하고, 인스턴스가 다시 Running 상태가 되면 변경된 속성을 반영한다.
- 인스턴스를 새로 생성하지 않고 Boot Volume을 교체한다.
- 지원되는 속성 변경에만 사용할 수 있다.
  - BootVolumeSizeInGBs
  - ImageId
  - KmsKeyId
  - KubernetesVersion
  - NodeMetadata
  - SshPublicKey
- maxSurge가 아닌 maxUnavailable 중심으로 병렬성을 제어한다.
- 인스턴스 자체를 유지해야 하는 운영 정책이 있을 때 고려할 수 있다.

## 3. 주요 파라미터
### 3.1. Maximum surge, maxSurge
maxSurge는 Replace nodes 방식에서 Node Cycling 중 일시적으로 추가 생성할 수 있는 최대 노드 수 또는 비율을 의미한다.

값이 클수록:
- 더 많은 새 노드를 먼저 생성할 수 있다.
- 서비스 가용성을 유지하기 쉽다.
- 업데이트 병렬성이 증가한다.
- 일시적 비용과 quota 사용량이 증가한다.

### 3.2. Maximum unavailable, maxUnavailable
maxUnavailable은 Node Cycling 중 동시에 unavailable 상태가 될 수 있는 기존 노드 수 또는 비율을 의미한다.

값이 클수록:
- 더 많은 노드를 동시에 Drain 및 교체할 수 있다.
- 작업 완료 시간이 짧아질 수 있다.
- 워크로드 가용성 저하 위험이 증가한다.
- PDB 또는 리소스 부족으로 Drain이 실패할 수 있다.

> **예시:**  
> **기존 노드 제거 및 새 노드 생성 방식** (`maxSurge=1`, `maxUnavailable=1`)
> - 기존 노드 1개를 unavailable 상태로 만들 수 있고, 새 노드도 1개까지 추가 생성할 수 있다.
> - 상황에 따라 일시적으로 추가 노드가 생성될 수 있으며, 이 경우 비용이 증가할 수 있다.   
>   -> 다만 maxUnavailable을 함께 허용하므로 안정성 우선 방식보다 전체 작업 시간이 짧아질 수 있다.
> - 노드 수가 일시적으로 감소한다. → 파드 재배치 안정성 감소
> - 비용 증가를 일부 억제하면서 속도를 높일 수 있지만, 애플리케이션 가용성 검토가 필요하다.
{: .prompt-tip }

> **기존 노드 제거 후, 새 노드 생성 방식** (`maxSurge=0`**,** `maxUnavailable=1`)
> - 새 노드를 먼저 만들지 않고, 기존 노드를 먼저 Unavailable 상태로 만든다.
> - 지정한 노드 수 안에서 업데이트/업그레이드 가능하다. (비용 추가 발생하지 않음)
> - 추가 비용 발생은 최소화하지만, 서비스 가용성을 저하시킬 수 있다.
{: .prompt-warning }

### 3.3. 기본값 및 제약 조건
Replace nodes 방식에서 maxSurge와 maxUnavailable을 명시하지 않으면, 기본적으로 `maxSurge=1`, `maxUnavailable=0`이 적용된다.

제약 조건:
- maxSurge와 maxUnavailable을 모두 0으로 설정할 수 없다.
- 값은 정수 또는 백분율로 지정할 수 있다.
- 두 값은 모두 정수이거나 모두 백분율이어야 하며, 정수와 백분율을 혼합할 수 없다.
- 정수로 지정하는 경우 Node Pool의 Node count를 초과하지 않도록 설정한다.
- maxSurge를 사용하는 경우 추가 노드 생성을 위한 quota가 필요하다.
- maxUnavailable 값이 PDB 또는 워크로드 정책과 충돌하면 작업이 실패할 수 있다.
